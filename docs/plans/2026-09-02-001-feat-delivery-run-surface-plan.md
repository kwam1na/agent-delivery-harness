# feat: Delivery run surface — emitted run events, local store, operator viewer

**Target repos:** `agent-delivery-harness` (event contract, store, `emit`, viewer, verify row, package publish), `agent-skills` (emit points in the workflow skills, lens-selection rule), and the two adopters `athena` and `agent-delivery-harness` (installation and guidance). Paths are relative to the repository named in each unit.

**Plan finish line.** The run surface exists in the harness; both adopters run the workflow release that names the emit points; and one ordinary delivery in each adopter shows in the viewer with its lens selection, every review round bound to its candidate, cost on each closed round, its gate outcome, its decisions, and its end. In the harness the gate and record outcomes are CLI-written and the verify row reports the journal complete; in Athena, which runs no product command and does not run the product's verify, the gate outcome is executor-reported and the viewer's readout reports `complete-executor-only`, labeled unbound to a record.

---

## Summary

Every delivery run today leaves its most valuable data in the coding host's transcript: which lenses the executor chose and why, how many review rounds ran and on which candidate, what the gate and recorder did, what the executor decided at each fork, and what it cost. The operator learned this after the MVP proofs only by reading three transcripts by hand. The product emits evidence, not run data, and Athena's own telemetry record captures a summary after the fact rather than the run as it happens.

This plan adds a run surface: a small, self-attested, append-only event journal per delivery run, written by the product's CLI commands automatically and by the executor at named fork points through one `emit` command; a per-repository local store outside any candidate tree; a CLI and a single local page that render runs live and after the fact; and a verify-time row reporting whether a recorded delivery left a complete run journal. Executor decisions become emitted events instead of something mined from transcripts.

Operator decisions that bound this plan (2026-09-02): local store first, no remote sink; emission by command, not by file drop; cost is included and executor-reported; review acquisition stays with the executor, so the product mandates only its two shipped lenses (correctness and testing) and the executor selects any others by the depth of the delivery and records the choice.

## Problem Frame

The MVP proofs (V26-1082 in Athena, V26-1540 in the harness) showed three things the product cannot see:

1. **Executor judgment is invisible.** Lens selection, branch naming, when a converged review counts as satisfied, whether a mutating lens gets its own worktree, and which skills were invoked versus read were all decided in-transcript. None reached the ticket or the record.
2. **Run shape is invisible.** Round count, the candidate each round bound to, gate duration, recorder outcome, and the moment the PR opened exist only as host tool calls. The double review loop in V26-1082 was caught by the operator watching the transcript.
3. **Cost is invisible to the product.** The host knows tokens and duration; the product records nothing.

Athena's `delivery:telemetry-record` captures iteration and finding counts and gate spans into a committed file after the gate, which is a summary, changes the candidate after the gate proved it, and exists only in Athena. The harness `telemetry` block in `delivery-evidence/1` counts passes over one candidate for the validator's sake and is not observability.

## Requirements

- R1. A run journal exists per delivery run, append-only, one file, with a stable run id, and every event carries the run id, a sequence number, an instant, the repository, the ticket and the candidate tree SHA on the kinds whose payload names them (the run's ticket is read from `run.started` or `ticket.read`), and the actor that wrote it.
- R2. The seven candidate-facing product CLI commands (`check`, `prepare`, `review-context`, `submit-evidence`, `gate`, `record`, `verify`) append their own completion event automatically when a run is current for the invoking worktree. No executor action is needed for those. Automatic emission is best-effort and can never change a command's outcome or exit code. `managed`, `maintain`, `emit`, and `runs` are not wrapped. An adopter whose gate is not a product command (Athena's `pr:athena`) has the executor report the gate outcome instead.
- R3. The executor emits events at named fork points through one CLI command. The workflow skills say where. The set in v1: run started and ended, ticket read, posture declared, lenses selected with rationale and the mandated pair, review round opened and closed with findings by severity and cost, pull request opened, blocker recorded, decision recorded, compounding recorded.
- R4. Cost is required on every closed review round and on run end as `{unit, total, reportedBy}` and is self-reported.
- R5. The store is local to the repository under the git common directory, outside any candidate tree, survives worktree removal, owner-only, and is never a protected authority path or a review-neutral path in a candidate. It is shared by every worktree of the repository: anything the owner executes in any worktree, including candidate scripts, can read and append it, and can seal a live run by appending `run.ended`. That is acceptable only because nothing authoritative reads it (R6). A seal through another worktree's `--run` leaves this worktree's pointer, so later appends, wrapped completions included, are rejected into a bounded note in the store's notes subdirectory, which the viewer surfaces; a seal through this worktree's own pointer clears it (D3), so later wrapped completions write nothing, and that seal is visible only as a premature `run.ended` whose completeness readout lists whichever of `command.completed:gate` and `command.completed:record` the seal preceded as missing.
- R6. Run journals are observability, not evidence. No gate, admission, or record decision consumes them. Verify reports their completeness as a self-attested row and, only when an operator opts in locally, may fail on it.
- R7. An operator can list runs and read one run as a timeline from the CLI, and can open a local page that renders runs live across one or more repositories named by path.
- R8. Secret discipline reuses the spine's detection and redaction rules with a free-text member set owned by the run family; structural members reject on a secret exactly as spine members do; the spine's own member set is untouched.
- R9. Zero runtime dependencies remain in the harness, proven by the standalone install sensor.
- R10. The mandated review lenses are the product's two shipped lenses, correctness and testing, under whatever names the repository gives them. The executor may add lenses and must record the selection and its rationale as an event whose mandated pair is non-empty.

## Scope Boundaries

In scope: the `run-event/1` contract and store in the kernel; the `emit` and `runs` CLI commands; automatic emission from existing commands; a manual publish of the harness packages carrying the `emit` command; emit points and the lens-selection rule in the workflow skills, released as a new `linear` profile release; installation of that release in both adopters; the Athena devDependency, script, and guidance that let Athena executors emit; a verify-time completeness row with a local opt-in requirement; one dogfood delivery per adopter observed through the viewer.

### Deferred to Follow-Up Work

- A remote sink or a cross-machine index (operator decision: local first). Cross-repository views in v1 are as wide as the repository paths the operator names.
- Replacing Athena's `delivery:telemetry-record` and its `telemetry.recorded` gate obligation. Athena's record keeps running unchanged in this plan; whether it becomes a derived summary of the run journal is decided after the first Athena run through the surface.
- Making the run journal a required input to any CI check, gate, or admission path. Until the store has an integrity story, the requirement flag is for operator-invoked local verify only.
- Productizing review acquisition (V26-1541 keeps its scope: make `obtain-review` realizable on the host without the missing Python module). This plan only makes the lens choice a recorded event.
- Any spine journal revision. Run events are a separate family by design (D1).
- Host-side automatic capture of tool calls or transcripts.
- Store retention and pruning, and automatic release-workflow publication.

### Institutional Learnings

- Three transcript inspections (V26-1512, V26-1082, V26-1540) produced the same categories every time: lens choice, branch naming, review-loop shape, shell friction, hand-supplied values. Those categories are the v1 event vocabulary; branch naming is a `decision.recorded` fork by name.
- A converged review on an unchanged candidate was re-run in Athena because guidance read as unconditional (V26-1544). A `review.round.opened` event carrying the candidate tree SHA makes that visible the moment it happens.
- Athena's telemetry commit after the gate changed the candidate. A store outside the tree has no such effect.
- Executors under-report judgment calls in their final text. An emitted `decision.recorded` at the fork is cheaper than mining and is checkable.
- On the dogfood host every shell call is a fresh process and subagents inherit no exports. A run id carried only in the environment never reaches the gate or recorder.

## Key Technical Decisions

- **D1. Separate family, not spine kinds.** `run-event/1` is a new contract with its own validator and store. It reuses the journal store's file mechanics and secret discipline but has no reducer, no expected revision, and no fence. Reason: adding spine kinds is a contract-freeze revision, and run events must never be able to advance or block a delivery.
- **D2. Store at `<git-common-dir>/managed-delivery/runs/`, one `<run-id>.jsonl` per run, plus a `current/` directory of per-worktree pointers.** This is the facade's namespace, chosen deliberately over the record store's worktree-private root because a run must outlive its worktree, which is removed after merge. The departure's consequence is stated in R5. The run store is always this location under this fixed namespace, independent of `config.storageNamespace`, so config-free and config-bearing commands agree. Directories `0o700`, files `0o600`; every create, append, and read of a journal, note, or pointer file refuses a symlink at the final path component (pointer create by exclusive create; pointer read, journal, and note opens by `O_NOFOLLOW`, with ownership, mode, and regular-file checks by `fstat` on the opened descriptor rather than a separate lookup) or a file not owner-only; directory components are not defended, since node has no `openat`. That refuses a planted symlink at a file outside a race; the residual window against owner-executed code is unclosable and is bounded by R6 because nothing authoritative reads the store. The kernel exports a namespace resolver (git common directory from the invoking worktree, taking its runner and environment from the caller and resolved for the run store with the git environment cleared) that the facade also uses; the record store's refusal of common-directory namespaces is unchanged. Cross-repository views are the viewer's job (`--repo` may repeat).
- **D3. The current run is a per-worktree pointer in the store, not an environment variable.** The pointer key is the digest of the invoking worktree's absolute `--git-dir`; it is config-independent, differs per worktree, and is not the record store's `workspaceId`. `emit run.started` allocates the id and writes the pointer with exclusive create, refusing when one already exists unless `--force` is given, in which case the new `run.started` payload carries the displaced run id in its structural `displacedRunId` member, bounded to the run-id charset; `emit run.ended` clears the pointer only if it names that run. `emit` resolves its run as `--run` if given, else the pointer for its worktree, else nothing; a wrapped command resolves by the pointer only, since its argument surface does not change, so after `run.ended` has cleared the pointer it appends nothing and writes no note. `verify` locates the journal for its completeness row by the record's tree SHA (U6), not by the pointer, so an ended run is still reported. When more than one journal binds the record's tree SHA, which a `--force` restart or a premature seal makes ordinary, `verify` evaluates the one `findByCandidateTreeSha` selects and names the other matching run ids in the row; none yields `absent`. An explicit `--run` resolves only when its id passes the charset check and its journal file exists, that existence check being the same `O_NOFOLLOW` open with `fstat` on the descriptor that a journal read uses, so a symlink or a non-regular, non-owner-only file at the journal path reads as no journal; otherwise it is no resolvable run, so no note or journal is ever created for an arbitrary id. A pointer whose content fails the charset check or whose journal file is missing likewise reads as no current run. A lens subagent working in another worktree of the same repository passes `--run` explicitly, so one delivery is one run; `--run` names a run in the store resolved from the invoking worktree (the repository's shared common-directory store), so a lens realized in a different repository has no run to pass and emits nothing. Run ids match a bounded charset; a malformed id from any source is rejected before any path is formed, and the resolved path must be contained in `runs/`; pointer reads are size-bounded. Reason: the environment does not survive on the dogfood host. No other user can plant a pointer; anything the owner executes can, including candidate scripts, which is why nothing authoritative reads the store (D5).
- **D4. One `emit` command, kind-typed, payload as JSON on stdin or `--json`.** The validator rejects unknown kinds and malformed payloads at write time; kind validation precedes payload validation, so an unknown kind is rejected as an unknown kind, named in the output, whatever its payload. `command.completed` is CLI-writer-only; `emit` refuses it. `emit` and `runs` are a config-free command class with their own context type, dispatched before `harness.config.ts` loading, so other commands' `config_unloadable` timing is untouched and the pair runs in a repository without a config. The only thing a config-free command may do with `harness.config.ts` is an existence check (`lstat`, no follow) at a worktree root; it never imports, loads, or parses it. Outside a git repository a config-free command exits with the policy code naming the missing repository and writes nothing; `emit` of any kind other than `run.started` with no resolvable run (no `--run`, no pointer) likewise exits with the policy code and writes nothing, since there is no run to note against; run resolution precedes kind validation. `run.started` is the one kind that needs no run, because it allocates one; `run.ended` requires one. Reason: operator decision, write-time validation is why a command beats a file drop, and Athena has no config.
- **D5. Self-attested, observability only.** Every event carries `attestation: "self"`. The CLI `verify` reads the store and passes a `runJournal` row into the pure `verifyDeliveryRecord` through its options; the row is echoed in the result labeled self-attested and is absent when no caller supplies it. `--require-run-journal` fails on any status other than `complete` (so `absent`, `incomplete`, and `complete-executor-only` all fail), compares the status string by exact equality, and is for operator-invoked local verify only, never CI, gate, or admission, until an integrity story exists. Nothing else reads the store. Reason: R6; the store is reachable by anything the owner runs, so a self-reported journal must not be able to pass or fail a delivery in any authoritative path.
- **D6. Cost is executor-reported using the existing `{unit, total, reportedBy}` shape, required on every closed round and on run end.** Reason: the product cannot measure host cost; the grammar already has the shape; optional cost was never recorded in practice.
- **D7. Lens mandate is the product's two shipped lenses; selection beyond them is the executor's.** Correctness and testing are mandated under the repository's names for them (both repositories declare the same pair, `lens.outcome-correctness` and `lens.adversarial-testing`, the latter in the `testing-policy` category; the harness references the shipped charters for them by identity, `persona.outcome-correctness` and `persona.testing-policy`, resolved from its installed generation). Any other repository-declared or executor-chosen lens is executor-selected and recorded in `lens.selected` with `mandated` (the pair), `selected`, and `rationale`. Completeness checks the pair's identity only when the operator supplies it: the CLI `verify` accepts a repeatable `--mandated-lens <id>` and passes the ids to the evaluator; the product CLI hardcodes no repository path and reads no candidate-controlled file for them (the harness's `.agents/policy` and its installed generation under `.agent-skills/` are candidate-committed content), and each adopter's root `AGENTS.md` names its two ids so the operator can pass them. Without that input the check is arity-and-non-empty only, and the pair's identity is confirmed in the dogfood inspection. The `AGENTS.md` declaration is candidate-committed, so an executor could widen it in the same candidate before emitting `lens.selected`; like D12, the check bounds accident, not tampering, and nothing authoritative reads it. `obtain-review` and `review-work` keep the caller-selected list. Reason: operator decision; a repository must not be able to widen what counts as mandatory; V26-1541 stays separate.
- **D8. Viewer is a CLI first, then one static page.** `runs list` and `runs show <id>` render from the store; `runs serve` starts a dependency-free local HTTP server over `node:http` that serves one inline HTML page and a JSON endpoint over the same files, polling for live updates. A run is live when its worktree pointer names it and it has no `run.ended`; for each `--repo` path the server computes that worktree's own pointer key from the same `git rev-parse --path-format=absolute --git-dir --git-common-dir` query that resolves its store root (which like the toplevel query reads no index and runs no hook, alias, or pager), both queries run in that path with the git environment variables cleared, and reads only that pointer, never enumerating `current/`, so `--repo` must name the worktree a run is executing in for it to read as live, and a run live in an unnamed worktree renders as open but not live; `runs list` marks runs without `run.ended` as open. The server binds loopback on an ephemeral port by default, rejects requests whose `Host` is not the bound loopback address and port, serves JSON with `nosniff` and a restrictive content security policy, sends no cross-origin allowance, and escapes every rendered string, store-derived or not, including the root path in the config-presence note. Reason: the CLI alone replaces transcript mining; the page is the bird's-eye view; executor-written free text must not script the operator's browser.
- **D9. Athena emits through the published CLI as an exactly pinned devDependency invoked by a package script.** Athena pins the exact version so the frozen lockfile carries integrity, adds a `package.json` script that runs the installed package's CLI entry (`node_modules/@agent-delivery-harness/cli/src/main.ts`, not the `exports` barrel) under bun, and guidance names that script. No `bin` entry is added: nothing in this plan executes the package by name. No invocation resolves a package name from the network at run time. The entry is TypeScript, and node refuses to strip types for anything under `node_modules`, so the installed package runs under bare node in no form: Athena is bun-only and its script invokes the installed entry file directly under bun; node executes the shipped TypeScript only through a loader, which is why the harness's standalone install sensor keeps its `tsx` loader and runs the installed entry file through it. Publishing is a manual operator step (there is no publish workflow — superseded by the operator decision of 2026-09-02 recorded under U2p) and bumps every package and `HARNESS_VERSION` in lockstep, which changes preparation-receipt fingerprints for runs prepared after the bump; no recorded delivery changes. Athena does not adopt the kernel as its recorder. Reason: the smallest path that lets Athena executors emit without vendoring or a network-resolved name.
- **D10. Skill text names an optional, repository-declared emit capability; adopter guidance supplies the command; enforcement is verify's row, not skill prose.** Core skills stay product-neutral: they say "emit `<kind>` through the run-event command the repository's root `AGENTS.md` declares, when it declares one". The capability is optional: when absent, the executor proceeds silently with no handoff and no blocker. Reason: no core skill names a product command today; an absent optional capability must not block a delivery (R6); prose rules were how the double loop happened.
- **D11. Candidate binding key is the tree SHA.** Events that bind to a candidate carry `candidateTreeSha`, the value `prepare` reports and the record's `treeSha`; `prepare` gains a labeled machine-readable line for it. Reason: records carry no commit SHA.
- **D12. Completeness is ordered by `seq`, and the ordering bounds fabrication cost, not fabrication.** The checked constraints are exactly these: `run.started` is `seq` 1 and the store rejects a second `run.started` on the same run; `ticket.read`, `posture.declared`, and `lens.selected` precede the first `review.round.opened`; each `review.round.opened` precedes its `review.round.closed` on the same round; at least one closed round (on the record's tree SHA when the evaluator is given one, any closed round otherwise) precedes the `gate` completion; the `gate` completion precedes the `record` completion; `pr.opened` follows the `gate` completion; `run.ended` is last and the store rejects any append after it. Each constraint anchored on one or two anchor events (the `gate` and `record` CLI completions, or, in an executor-only journal, `gate.reported`) is evaluated only when every anchor it names is present in the journal; when any is absent the constraint is skipped and the absent anchors are reported missing under the names the required-entry constant fixes, whatever else the journal holds. `gate.reported` is ordered only in an executor-only journal (no `command.completed` at all), where it takes the gate completion's place: at least one closed round (on the record's tree SHA when the evaluator is given one, any closed round otherwise) precedes it and `pr.opened` follows it; in a journal that has any CLI completion `gate.reported` carries no ordering constraint and the CLI completion's constraints govern. Nothing else is ordered. The evaluator applies to any journal. A hostile executor can still batch-emit a plausible journal; the rule makes that a deliberate act rather than an afterthought, and nothing authoritative depends on it.
- **D13. A run may carry more than one ticket, and the binding is an optional member rather than adjacency.** Amended 2026-09-03 under V26-1658, from the V26-1558 dogfood: one run carried the dogfood ticket at `sensor-only` and the ordinary ticket it delivered at `characterization-first`, and `run-event/1` had no way to say which posture belonged to which — the executor emitted both `ticket.read` entries and both postures and left the pairing to adjacency, while `gate.reported` and `pr.opened`, being payload-closed, refused a `ticket` outright (`unknown_member at /payload/ticket`, visible on that run's refused-appends note). `posture.declared`, `gate.reported`, and `pr.opened` therefore each take an OPTIONAL `ticket` of the same shape `ticket.read` uses, envelope-mirrored and held to exact agreement like every other mirrored member. The alternative — declaring a run to carry exactly one ticket, so a dogfood delivery is two runs — was rejected: it splits one delivery's journal in two, and the store's per-worktree pointer makes two concurrent runs in one worktree unrepresentable. The run's PRIMARY ticket is the first the journal names in `seq` order, which is `run.started`'s when a run named one at the start and the first `ticket.read`'s otherwise; an entry that omits `ticket` binds to the primary, which is what every existing single-ticket journal already means. The member is never required: completeness names it in neither its required entries nor its constraints, so a journal written before this amendment evaluates exactly as it did. The viewer renders an entry's own binding on its row and nothing on an unbound one, the runs table naming the primary once per run.

## High-Level Technical Design

**Event envelope (`run-event/1`).** `{version:"run-event/1", runId, seq, at, repo:{commonDir, remote?}, kind, actor:{role:"cli"|"executor", id?}, ticket?, candidateTreeSha?, attestation:"self", payload}`. `seq` is store-assigned and strictly increasing per run. `at` is the writer's instant at write time, set by the emitting CLI process and not settable through `emit`'s argument surface; no literal instants anywhere in code. `actor` is set by the writing process and is not settable through `emit`'s argument surface or payload: the boundary wrap writes `role:"cli"`, `emit` writes `role:"executor"`, `id` is omitted in v1, and the store's `append` rejects an event carrying `role:"cli"` on any kind other than `command.completed`, so the viewer's writer labels and the evaluator's CLI-completion check rest on the store boundary rather than on `emit` alone. `emit` copies `ticket` and `candidateTreeSha` into the envelope from the payload of any kind that carries them, and every reader reads the envelope member only; the store's `append` rejects an event whose envelope member disagrees with the payload's: absent where the payload carries one, present where the payload does not (on any kind, including one whose payload never names it), or differing. That holds the invariant at the store boundary rather than in `emit`; v1 has no other appender of these kinds (the boundary wrap writes only `command.completed`, which carries neither member), so the check is exercised by U1's direct-store vector and guards future callers. Both members are bounded wherever they appear: `candidateTreeSha` to a lowercase hexadecimal git object id of 40 or 64 characters, `ticket` to the kernel's existing `RUN_ID` charset and length (`^[A-Za-z0-9][A-Za-z0-9._-]*$`, 128), rejected at validation in payload and envelope alike.

**Kinds and payloads (v1).**

| Kind | Writer | Payload |
| --- | --- | --- |
| `run.started` | executor | `{ticket?, host, workflow:{releaseId, profile}, displacedRunId?}` |
| `run.ended` | executor | `{result:"complete"|"partial"|"blocked", cost}` |
| `ticket.read` | executor | `{ticket, posture?, tracker}` |
| `posture.declared` | executor | `{posture, ticket?}` |
| `lens.selected` | executor | `{mandated:[2 ids], selected:[], rationale}` |
| `review.round.opened` | executor | `{round, candidateTreeSha, lenses:[]}` |
| `review.round.closed` | executor | `{round, candidateTreeSha, outcome, findings:{P0,P1,P2,P3}, cost}` |
| `command.completed` | cli only | `{command:<registered name>, outcome:<closed enum>, durationMs, digest?}` |
| `gate.reported` | executor | `{command:<free adopter label>, outcome:"pass"|"fail"|"blocked"|"interrupted", durationMs, ticket?}` (adopters whose gate is not a product command; viewer-only, never satisfies the harness completeness rule) |
| `pr.opened` | executor | `{url, candidateTreeSha, ticket?}` |
| `blocker.recorded` | executor | `{code, summary}` |
| `decision.recorded` | executor | `{fork, choice, cited?}` |
| `compounding.recorded` | executor | `{outcome, reference?}` |

`command.completed` carries no argv, stdout, stderr, or blocker text; `outcome` is a closed enum of the command's result categories. Lens ids in `mandated` and `selected`, and the values of `--mandated-lens`, are bounded to the `PROVIDER_ID` charset and length. `pr.opened.url` must be an `https` or `http` URL at validation, and the viewer renders it as text or a scheme-checked link, never a raw `href`. Free-text members under the run family's redaction set: `rationale`, `summary`, `choice`, `cited`, `fork`, each a scalar string, length-bounded like spine free text. `cited` is a locator or a short excerpt, never transcribed ticket or contract content; the journal is never read back as ticket authority. Every other member is structural and rejects on a secret. Named `decision.recorded` forks the skills call out: branch name, review re-run on an unchanged candidate, worktree for a mutating lens, skill read versus invoked, any value the executor supplied that should have been discoverable.

**Completeness.** A journal is complete for a record when it has `run.started`, `ticket.read`, `posture.declared`, one `lens.selected` whose `mandated` has two non-empty ids and, when the evaluator is given mandated ids, equals them, at least one `review.round.opened` paired with a `review.round.closed` on the same round whose `candidateTreeSha` equals the record's `treeSha`, `command.completed` written by the CLI for `gate` and `record`, `pr.opened`, and `run.ended`, all in the D12 order. `gate.reported` never substitutes for the CLI-written `gate` completion; a journal with no `command.completed` at all is executor-only and additionally requires `gate.reported`; when the journal satisfies every condition the complete rule states except the two CLI completions and carries `gate.reported` in its ordered place, its status is `complete-executor-only` with `command.completed:gate` and `command.completed:record` listed missing, which is Athena's finished state and never satisfies `--require-run-journal`. The evaluator's tree SHA is the record's `treeSha` when a record supplies one, which only `verify` has; the viewer supplies none, and with no tree SHA every constraint phrased over the record's tree SHA (the required paired round, the closed round preceding the `gate` completion, and the closed round preceding `gate.reported` in an executor-only journal) is evaluated over any `review.round.opened` paired with a `review.round.closed` on the same round, which the readout labels as unbound to a record; a journal in which no `review.round.opened` pairs with a `review.round.closed` on the same round is `incomplete` with `review.round.closed` listed missing as the unpaired required round, and `review.round.opened` listed missing as well when the journal has none, so an unbound `incomplete` always names what it lacks. Statuses are `complete`, `complete-executor-only`, `incomplete`, and `absent`; every reader compares them by exact equality. The status describes the journal, not the repository: any violation forces `incomplete` whatever the writer mix, a `mandated-pair-mismatch` from the arity-and-non-empty check or from the supplied-pair equality check alike and a `round-not-bound-to-record` from the tree-SHA-bound round check included. The readout adds the note "no CLI gate completion in this journal; `harness.config.ts` present at <root>" to a `complete-executor-only` journal when an existence check finds that file at the worktree root it renders for (each `--repo` path for `runs serve`, which must be a worktree root resolved by a git plumbing query that reads no index and runs no hook, alias, or pager (`git rev-parse --show-toplevel` has been verified to do so); the invoking worktree root for `runs show` and for `runs serve` with no `--repo`); the note is presentational, the file is candidate-committed so its absence is executor-suppressible, and like D7 it bounds accident, not tampering. Verify reports `runJournal: {runId?, alsoMatching?:[…], status, missing:[…], violations?:[…], attestation:"self"}`, where `missing` carries required entries by name and `violations` carries each violated constraint by name. The names `missing` can carry are likewise a closed set fixed by U1 as a second exported constant, enumerated here: `run.started`, `ticket.read`, `posture.declared`, `lens.selected`, `review.round.opened`, `review.round.closed`, `command.completed:gate`, `command.completed:record` (the two CLI completions, named by kind and command so each is its own entry), `pr.opened`, `run.ended`, and `gate.reported`; U1's suite asserts it as a literal list by exact equality in a fixed order, the evaluator emits `missing` names only as members of it, and one vector per entry, a journal satisfying the complete rule (or, for `gate.reported`, the executor-only rule) with exactly that entry withheld, has `missing` naming that entry and `status` `incomplete`, the union of `missing` names across those vectors equaling the constant, so a required entry an implementation silently drops fails the suite. Constraint names are a closed set fixed by U1 and enumerated here, one per ordering constraint D12 states for the evaluator (`run-started-not-first` and `run-ended-not-last` are the evaluator's own detections of conditions the store also guards at append time (a second `run.started`, an append after `run.ended`); the store's refusal is a separate enforcement with no identifier of its own, so those two reject vectors are journals written directly by the test, which no `emit` path can produce): `run-started-not-first`, `prerequisites-after-first-round` (the three prerequisite kinds preceding the first `review.round.opened`, one constraint), `round-closed-before-opened`, `gate-before-closed-round`, `record-before-gate`, `pr-before-gate`, `run-ended-not-last`, `gate-reported-before-closed-round` and `pr-before-gate-reported` for the two executor-only orderings, plus `mandated-pair-mismatch` for the arity-and-non-empty check on `mandated` and for the supplied-pair equality check and `round-not-bound-to-record` for the tree-SHA-bound paired round. The exported constant U1 owns is exactly this list, which U1's suite asserts first against these names as a literal list compared by exact equality in a fixed order, so adding, removing, or renaming an entry fails the suite, and a change to D12's constraints forces a visible edit here and in that assertion; the evaluator emits identifiers only as members of that constant, with no violation-identifier string literal elsewhere in the evaluator, a requirement the reviewer checks on the diff; and U1's suite covers the constant by one reject vector per entry (a vector being a full evaluator input `(events, treeSha?, mandatedLensIds?)`, each argument supplied or withheld as that entry requires) whose `violations` is exactly that entry and no other and whose `status` is `incomplete`, asserting that the union of `violations` identifiers observed across those vectors is the constant exactly, so an entry no journal can provoke in isolation fails; a `violations` entry is a product-defined name only and carries no journal-derived string.

**Store.** `createRunStore(commonDir)` with `allocate()` (bounded-charset id without `.`, collision-checked), `append(runId, event)` (validate, run-family secret discipline, assign `seq`, torn-tail repair, owner-mode append), `read(runId)`, `list()`, `current(worktreeKey)`, `setCurrent`, `clearCurrent`, and `findByCandidateTreeSha(treeSha)`, which scans `list()` (run ids in ascending order, so enumeration is deterministic) and `read()` through the same `O_NOFOLLOW`, `fstat`, and size-bounded read as any journal read, skipping a journal that refuses it, matches any event whose envelope `candidateTreeSha` equals the given SHA, and returns the most recently started matching run (highest `run.started` `at`; a matching journal with no `run.started`, or whose `run.started` `at` is unusable, sorts after every journal that has one; ties at any rank broken by the lexicographically greatest run id; `at` is second-granularity, so a same-second tie is deterministic but not temporal) with the other matching run ids, or none. A rejected append, automatic or explicit, writes one bounded line to `runs/notes/<run-id>.jsonl` (its own subdirectory, so no run id can name another run's notes; run ids exclude `.` and `list()` reads only journal files) carrying only the kind attempted (truncated to the `PROVIDER_ID` length bound and reduced to that charset, so an unbounded or hostile kind string never reaches the note), the rejection code, the discipline pattern id when that was the cause, and the instant, never the rejected payload or an error string, under the same discipline and modes; a note write that is itself refused (symlink or mode) is dropped with no further attempt, and a command's outcome and exit code never depend on any store failure.

**CLI.** `emit <kind> [--run id] [--json …] [--force]` (stdin when `--json` absent); `runs list|show <id>|serve [--repo path…] [--port n]`. The CLI viewer and `emit`'s diagnostics apply the kernel's existing display neutralization (ANSI sequences, bidi and zero-width characters, C0 and C1 control characters other than tab and newline, DEL, and the Unicode line and paragraph separators) to every string they render before it reaches the terminal, collapsing whitespace in every single-line field they print so free text forges no row; the page escapes the same strings as markup (D8). Both are config-free commands with their own context type. Every registered candidate-facing command's completion is wrapped once in the boundary and appends `command.completed` when a run resolves; `emit` and `runs` are excluded from the wrap.

**Skills.** `execute-work`: emit `run.started` before reading repository authority, `ticket.read` and `posture.declared` after, `decision.recorded` at any fork the executor resolves by judgment including the named forks above, `gate.reported` after a repository gate that is not a product command, `pr.opened`, `blocker.recorded`, `run.ended` with cost in the handoff. `obtain-review`: emit `lens.selected` before realization, `review.round.opened` per round, and pass `--run` to any lens realized in another worktree of the same repository (a lens in a different repository shares no store and is given no `--run`). `review-work`: emit `review.round.closed` with the reduced outcome and cost. `compound-learning`: emit `compounding.recorded`. `deliver-work`: state that the run id is host mechanics resolved from the store, not ticket content, and that the emit capability is optional and declared by the repository's root `AGENTS.md`.

- Home-directory store: rejected for v1, no convention exists and the operator chose local first; cross-repo is the viewer's concern.

- File-drop emission: rejected by operator; no write-time validation.
- Host transcript capture: rejected; host-specific and outside the product boundary.
- Extending Athena's telemetry record: rejected; post-gate, summary only, Athena-only, and it moves the candidate.
- Naming the product CLI inside core skills: rejected; core stays neutral, adopter guidance names the command.
- Making the kernel's verify read the store: rejected; it is pure by contract and shared with the action.

## Risk Analysis & Mitigation

- Executors skip emit points. Mitigation: verify's completeness row, the local opt-in flag, and the U7 gap lists; any CI adoption follows an integrity story.
- A lens subagent in another worktree writes to no run or the wrong run. Mitigation: `obtain-review` text passes `--run` for a same-repository worktree; an explicit `--run` resolves only against an existing journal, so a mistyped id writes nothing rather than starting a stray run; a well-formed id naming another live run is indistinguishable in that run's timeline, since the envelope carries no worktree key, and that residue is bounded by R6 and by the operator reading each round against the run's candidate tree SHA.
- A fabricated journal. Mitigation: `command.completed` is CLI-only, rounds must pair, ordering is enforced, the mandated pair is checked where its ids are known, and the flag never gates an authoritative path (D12).
- A run never ends, so its worktree pointer persists. Mitigation: the next `run.started` refuses unless forced; `runs list` shows open runs; a missing journal file reads as no current run.
- The store fills. Mitigation: `runs list` reports size; retention is a follow-up; files are small JSONL.
- Secret leakage in free text. Mitigation: the run family's redaction set and structural rejection, tested in U1; `command.completed` carries no command output.
- Athena's devDependency drifts from the installed release. Mitigation: exact pin with frozen-lockfile integrity, named in `AGENTS.md`; the lifecycle drift check covers the skills, the pin covers the CLI.
- The operator's browser is reached through the local server. Mitigation: D8 defenses tested in U5.
- The version bump for publishing changes receipt fingerprints mid-delivery. Mitigation: U2p lands between deliveries; a run prepared before the bump re-prepares after it.
